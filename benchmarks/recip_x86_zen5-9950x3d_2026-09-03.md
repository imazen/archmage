# recip/rsqrt: exact division vs Newton refinement — x86 (Zen 5)

The x86 half of the measurement the NEON exact-division fix left open.
`precise_reciprocals.rs` shipped NEON `recip()`/`rsqrt()` as exact division on
the strength of aarch64 measurements (`rsqrt_arm_neoverse-n1_2026-06-21.md`,
`rsqrt_f64_arm_apple-m4-pro_2026-08-02.md`) and pinned x86 f32 at 4 ULP with
"the decision left to an x86 run". This is that run.

## Setup

- Machine: AMD Ryzen 9 9950X3D (Zen 5) under WSL2, 32 threads. A scoring
  container was running concurrently on other cores; ratios were stable
  across 3 independent process runs (±5%).
- Toolchain: rustc 1.98.1 stable; **no** `-Ctarget-cpu=native` (runtime-dispatch
  build, what users get).
- Command: `cargo bench -p magetypes --bench recip_x86 --features std`
- Kernel: `f32x8<X64V3Token>` streaming load→op→store over 2048 L1-resident
  f32 (16 passes per measured iteration = 32768 lanes), inside one `#[arcane]`
  region so generic ops inline into AVX2 codegen.
- Code state: exact-division generator change applied (issue #64), measured
  pre-commit at base 6b5c0665 + working-tree change; the `newton1` kernels
  reconstruct the removed implementations from `rcp_approx`/`rsqrt_approx`
  plus one manual mul/sub Newton step.
- zenbench note: criterion_compat ran its single-pass protocol ("0 rounds"
  warning); figures are within-run means, cross-checked over 3 process runs
  (raw logs in the companion `.raw.txt`).

## Decision

Ship exact division anyway. In the full-precision tier, the documented
contract (0 ULP, `precise_reciprocals.rs`), IEEE rail behavior (issue #64:
`recip(±inf)` must be `±0`, not NaN), and cross-backend consistency
(NEON/WASM/scalar and all f64 widths already divide) outweigh a throughput
loss in an L1 microbench. `rcp_approx`/`rsqrt_approx` remain the unchanged
throughput tier for callers who want the estimate.

Per-arch picture for the same swap: Apple Silicon exact is FASTER (recip
1.35x, rsqrt 1.18x); Neoverse-N1 exact is slower (rcp 1.39x, rsqrt 2.15x);
Zen 5 exact is slower (recip ~1.9x, rsqrt ~3.6x).

## Follow-up (2026-09-04, final): tier split + branchless rails, zero new names

Resolution after the zen usage survey, the fearless_simd comparison, and a
rails-technique investigation (`~/tmp/railprobe`, results below):
`recip()`/`rsqrt()` are the WORKING tier — <= 4 ULP AND exact IEEE rails at
±0/±inf/NaN — by the fastest conforming path per backend, and the pre-existing
`recip_portable`/`rsqrt_portable` are the PRECISE tier (0 ULP incl. subnormals,
bit-identical free). An interim `_lowp`/`_midp` name set was dropped unshipped.

Rails techniques, all probe-verified on this box (NEON via qemu, spec-faithful):

- x86 128/256-bit: FMA-Newton + branchless rescue — the error term
  `e = 1 - a*r` is NaN exactly on rail lanes; `cmp_unord(e,e)` + `blendv`
  rescues them to the raw estimate, which is rail-EXACT on x86.
- x86 512-bit (V4/V4x native): rcp14/rsqrt14 + Newton + one VFIXUPIMM
  (tables 0x00870622 / 0x03830622, silicon-verified; rails premium +11.7%
  vs +181% for exact).
- NEON: FRECPS/FRSQRTS hardware-special-case inf*0 (→2.0/1.5) BY DESIGN, so
  recip was never rail-broken (our earlier docs were wrong); rsqrt fixed for
  FREE by forming the product inside the fused op: y*FRSQRTS(a, y*y).

Final numbers, this box (zenbench criterion_compat single-pass):

| kernel | ns / 32K lanes |
|---|---|
| hand-rolled rcpps+newton (no rails) | 1500 |
| **recip() bare — rails-correct working tier** | **1400** |
| recip_portable (0 ULP precise tier) | 1800 |
| hand-rolled rsqrtps+newton (no rails) | 1600 |
| **rsqrt() bare — rails-correct working tier** | **1900** |
| rsqrt_portable (0 ULP precise tier) | 5400 |

Interleaved min-of-400 probe cross-check: recip rescue +2.6%, rsqrt rescue
+20% over plain Newton; 512-bit fixupimm +11.7% (1050 vs 940ns, div 2640).
Contract pins: `precise_reciprocals.rs` — <= 4 ULP + rails on the bare names,
0 ULP + rails on `_portable`, every backend and width.
