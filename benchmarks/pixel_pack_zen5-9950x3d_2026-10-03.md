# Pixel packing on x86: `to_u8` and RGBA stores (Zen 5, 2026-10-03)

Bench: `magetypes/benches/pixel_pack.rs` (zenbench, interleaved). Host: AMD Ryzen 9
9950X3D, rustc 1.99.0, no `-Ctarget-cpu=native`. Provenance in the `.meta` file next
to this one.

## Why

The 0.9.29 AVX2 form, `cvtps` followed by saturating packs, returned **0** for +inf
and for values at or above 2^31. `cvtps` turns them into `i32::MIN`, which the packs
clamp to 0 instead of 255. AVX-512 inherited that form when its f32 block ops began
forwarding to AVX2 (3999a29); before that it ran the scalar default, which was
correct. Fix ff9e0a50 clamps with `min(255.0, x)` before `cvtps`.

These runs measure what that clamp costs, look for a cheaper correct form, and
decide the AVX-512 path.

## Method

- Each form streams an L1-resident buffer inside one `#[arcane]` region: 4096 `f32`
  for `to_u8`, 1024 pixels for the RGBA stores.
- zenbench runs the forms of one group interleaved, in shuffled order every round,
  and reports a 95% CI against the group's baseline.
- Before measuring, every correct form must match the scalar reference byte for byte
  on the benchmark data plus the edge values: 3e9, ±inf, NaN, 2^31, ±`f32::MAX`,
  255.5, 254.5, ±0.5 and 1.5.
- Zen 5 L1-resident loops have layout-sensitive performance, so run 4 rebuilt with
  `--cfg pixel_pack_redraw`, which inserts a padding function and shifts placement.

## Decisions

- **AVX2 keeps the `min(255)` clamp.** It is one float operation per plane, and no
  correct form avoids it: after `cvtps`, +overflow and NaN are the same integer. The
  clamp-both alternative moved between −2% and +3%, which is layout noise. The clamp
  costs 20–37% against the old wrong form.
- **AVX-512 `to_u8` uses `max(x, 0)` → `cvtps` → `vpmovusdb` at both widths.**
  Unsigned saturation maps the overflow value `0x8000_0000` to 255, so it needs one
  float clamp and no packs. It was faster than the V3 form in every run (0% to −40%;
  the size depends on layout) and never slower.
- **AVX-512 `f32x4::store_4_rgba_u8` packs two planes per 256-bit register**, then
  `vpmovusdb` and one `pshufb`: −40% to −43%.
- **AVX-512 `f32x8::store_8_rgba_u8` stays on the V3 form.** The only faster variant
  (−29%) uses 512-bit registers. An `f32x8` operation otherwise never touches zmm, and
  512-bit instructions can lower clocks on Skylake-SP and Cascade Lake. The 256-bit
  alternative was 9–13% slower.
- Measured on one Zen 5 machine only. Zen 4 runs 512-bit operations as two 256-bit
  halves, and Intel parts have different shuffle and narrowing costs. The adopted
  forms use fewer instructions than the ones they replace, but that has not been
  timed on other hardware.
