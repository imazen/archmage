# Generic token trampoline expansion

Checked with cargo-expand 1.0.126 and Rust 1.98.1 on x86_64, 2026-10-07.
The source dependency was main at `990aa7a7`; the arcane/common implementation
files are identical in this draft. This is an isolated probe, not a new API.

`src/main.rs` declares `work<T: HasX64V2 + OtherTrait>(token: T, ...) ->
T::Output`. OtherTrait gives V2 a u32 output and V3 a u64 output. The body also
calls V2::from_context, checking the enabled feature context. The source uses
forbid(unsafe_code); the expanded unsafe boundary is generated by arcane.

[cargo expand output](expanded.txt) shows a private inline sibling with V2
features and exactly the same generic bounds, argument types and associated
return type. The public always-inline wrapper asserts the actual archmage
HasX64V2 bound, then calls `__arcane_work::<T>(token, data)` inside the generated
unsafe block. It does not summon, erase, convert or replace the supplied token.
Passing V3 preserves T = X64V3Token but does not upgrade the declared V2 features.

The release run passed both typed assertions and printed
`V2 -> u32 5; V3 -> u64 6`; see [run.log](run.log). This verifies preservation of
the concrete generic token and its associated behavior. It is not an assembly
or compile-time performance comparison.

Reproduce from this directory with `cargo expand --bin arcane-generic-token-probe`
and `cargo run --release`, first copying `dependencies.lock` to `Cargo.lock`, and using a resource-limited
build wrapper. The justfile records both commands with caller-chosen log paths.
Expansion output is evidence, not source to paste back into a forbid-unsafe crate:
textual expansion does not preserve the original macro hygiene/lint provenance.

Design implication: retaining a generic token parameter in a proof entry is
mechanically compatible with this trampoline pattern. Removing that parameter
or concretizing T is the separate API change. Attune's existing-generic-entry
syntax remains undecided; genericity itself does not require legacy arcane.
