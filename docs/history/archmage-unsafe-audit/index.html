Archmage Unsafe Audit

Archmage lets safe Rust run CPU-specific SIMD code. Two kinds of unsafe make that possible: the trampoline #[arcane] generates to enter a #[target_feature] function, and the byte-level copies and views magetypes uses to move data between arrays and registers. This page lists every unsafe in the three crates, the proof each relies on, and what checks that proof.

The short answer

Is simd_storage.rs the one file in magetypes with unsafe {}? Yes, and the compiler enforces it. magetypes’ crate root denies unsafe_code and allows it only on mod simd_storage, and cargo xtask soundness rejects the keyword, and any other allow(unsafe_code), anywhere else in magetypes. The file holds all of it: 14 unsafe blocks, the Pod and TokenStorage traits and their impls, and one unsafe fn declaration. Before 7e49ccac it was almost true: a five-line SSE2 helper in the generated x86 backend, 30 generated TokenStorage impls and that declaration sat elsewhere, and only a text scan kept new unsafe out.

The backends’ 5,419 intrinsic calls need no unsafe of their own. Each backend method that calls an intrinsic is an #[arcane] region, for the receiver’s token or, for SSE2-only arithmetic, X64V1Token, so its unsafe is the macro’s trampoline, and rustc checks each call against the region’s features. The unsafe_code lint skips that output because it comes from another crate’s proc macro; its soundness argument is archmage’s, in the next section.

Why we think it is sound: the trampoline’s unsafe is discharged by a token, a value only detection or an already-proven feature region can create, and the macros check that the token is archmage’s own type. simd_storage.rs moves only bytes that are valid at every bit pattern, checks sizes and alignment at compile time, and bounds every gather and scatter lane against its slice. Getting around it takes deliberately shadowing archmage’s type names and hidden constants, and what that buys is undefined behavior in the forger’s own code, usually a SIGILL crash.

Trampolines

You write a function that takes a token. #[arcane] splits it in two: a hidden sibling that carries #[target_feature], and a wrapper with your function’s name and signature that calls the sibling inside unsafe. These are the committed expansion snapshots for the simplest case:

The obligation is narrow. Since Rust 1.86 a safe function can carry #[target_feature], and calling it is safe only from a function whose own features cover it. Anywhere else rustc requires unsafe, because running those instructions on a CPU without them is undefined behavior, in practice SIGILL. The wrapper is ordinary code, so its call needs the block. The sibling’s body stays checked safe Rust: value intrinsics are safe calls inside it, and import_intrinsics supplies the reference-based memory operations from safe_unaligned_simd.

The macro emits that call from one template, with the justification written next to it. quote! drops comments, so the expansion itself carries none:

The proof is the token argument. A value of type X64V3Token exists only if one of these happened:

  • X64V3Token::summon() returned it, after runtime detection or because every feature is enabled at compile time;
  • safe code called X64V3Token::from_context() from a function whose #[target_feature] covers V3, which rustc checks;
  • a stronger token was downcast, as in v4.v3();
  • someone wrote unsafe { X64V3Token::from_context() } and took the obligation on themselves.

The first three reduce to detection or to an enclosing feature region, and that region was entered the same way. So inside the wrapper the features are present, and the call is sound.

Is it really archmage’s token?

The macro picks the feature list by reading the token’s type name, and a name can lie. So the wrapper’s first line checks the type: each archmage token carries a hidden constant named after its own tier tag.

A local struct X64V3Token has no such constant and fails to compile with E0599. use archmage::X64V2Token as X64V3Token resolves to V2, whose constant is __ARCHMAGE_ASSERT_TIER_8CCD97C6, so it fails as well. Tier-trait bounds such as token: impl HasX64V2 get a different check: the macro restates the bound through the absolute path ::archmage::HasX64V2, which a local trait of the same name cannot satisfy.

That only works because the tier traits and SimdToken are sealed. The trait inside the private module is public, so it can appear in public bounds, but no outside crate can name it to implement it:

Methods, receivers and the backends

A trait impl can’t gain sibling functions, so #[arcane(_self = Type)] nests the feature-enabled function inside the method instead:

Every generated magetypes backend method uses this form, with the token as the receiver. In impl F32x4Backend for archmage::X64V3Token, self is the proof. The generator passes suppress_const_test, which omits the tier-constant check; that is acceptable there because the generator writes the real type path, never a user-supplied name.

Because these files contain no unsafe at all, rustc itself checks every backend intrinsic call against the enclosing #[arcane] region: the receiver’s token, or X64V1Token inside sse2_baseline!, whose SSE and SSE2 region inlines into callers without AVX. An AVX2 intrinsic in a V2 region does not compile. The exploit suite compiles sse2_baseline! straight from the generated file, in a trait impl for X64V3Token, with an AVX intrinsic in the body, and requires E0133 as the only error; a control with an SSE intrinsic must compile. What remains is the trampoline argument above, that the region’s features are proven by the token. cargo xtask soundness re-checks the same calls independently from the stdarch intrinsic database.

#[rite], incant! and #[autoversion]

#[rite] emits no unsafe. It puts #[target_feature] and #[inline] on your function and leaves the call-site check to rustc:

incant! summons tokens and calls the token-taking variants, which are safe #[arcane] wrappers, so it emits no unsafe either. #[autoversion] builds #[arcane] variants plus a dispatcher of the same shape. Its two unsafe templates apply only when your function is itself unsafe fn: the dispatcher is then unsafe fn too and passes your contract through.

Other platforms

aarch64 uses is_aarch64_feature_detected!, with two exceptions. On macOS, Mac Catalyst and aarch64 simulators, the Apple Silicon baseline features (neon, crc, rdm, dotprod, fp16, aes, sha2, sha3, fhm, fcma) are reported present without a runtime check, because those targets only run on M1 or later; tests/apple_fallback_guard.rs pins the target list. On Windows, detection goes through winarm-cpufeatures, which decodes the ID_AA64 feature registers from the Windows registry.

WASM has no runtime detection. summon() returns a token only in builds with simd128, and a WebAssembly engine validates every instruction when it loads the module, so a module that runs at all has the feature:

For a foreign architecture, such as an x86 token in an ARM build, there is no feature region to check against, so the only constructor is an unsafe fn whose contract cannot be met. Archmage never calls it, and summon() returns None there:

The testing switches can only remove proofs. dangerously_disable_token_process_wide(true) marks a token and its descendants unavailable; false resets them to “not yet detected”, so the next summon() detects again.

simd_storage.rs

magetypes keeps all of its unsafe in one file, magetypes/src/simd_storage.rs, so auditing it means reading one file. The compiler enforces that: the crate root denies unsafe_code, and the only allow is on this module.

The scanner checks the same thing in the source text, so it also covers code compiled out for the host’s architecture, and it rejects any other allow(unsafe_code):

The same rules reject a gather or scatter intrinsic outside this file, an unsafe impl Pod outside it, and MaybeUninit, mem::zeroed or token forging anywhere in magetypes.

Pod: bytes that are always valid

Every copy and view in the file requires Pod on both sides: every byte initialized, every bit pattern valid, no pointers, no interior mutability. Implementations go through impl_pod!, which also asserts that a type’s size equals the sum of its fields, so a type with padding cannot register. The registered types are the integer and float scalars, arrays of Pod types, and the stdarch vector types.

TokenStorage: vectors that carry a token

Vector wrappers such as f32x4<T> hold their token as a zero-sized field. If wrappers were Pod, copy could make a wrapper, and with it a token, out of arbitrary bytes. So they implement a separate trait, TokenStorage, and every helper that produces one takes a token of the right type as an argument:

The layout half of the contract is checked at compile time for every wrapper. impl_token_storage! fails to expand unless the wrapper is built from exactly (T::Repr, T), and every helper evaluates the impl’s LAYOUT constant, which asserts that the representation sits at offset 0 and fills the wrapper, along with check_token_layout’s zero size and alignment one for the token. Swapped fields (E0308), an extra field (E0061) and a non-zero-sized token (E0080) each fail to build; I checked all three with a local probe crate. Backend Repr types are bound by Pod, and the backend traits are sealed, so no outside crate can add a backend with a non-Pod representation:

Gather and scatter

AVX-512 gathers and scatters take a base pointer and sixteen signed 32-bit offsets, so the borrowed slice alone proves nothing about the addresses touched. The module states its bounds argument first:

It then quotes Intel’s Intrinsics Guide entry (synopsis, instruction, description and pseudocode) for each of the nine intrinsics it uses, and every SAFETY comment cites the Operation it relies on. Three entries carry the argument: the unsigned compare that builds the lane mask, and the masked gather and scatter, whose pseudocode touches MEM only inside IF k[j]. Intel’s MEM is addressed in bits, so the * 8 turns the byte offset index * scale into bits.

The helpers bound every enabled lane before the instruction runs. The wrapping gather masks the index; the slice gather and the scatter build the lane mask with that compare:

The 231 cap keeps every enabled offset non-negative after the instruction sign-extends it, and masked-off lanes touch no memory, so an empty slice is fine.

Known limits

Evading the check on purpose

The tier constant rejects accidental collisions. Evading it without unsafe takes deliberate work: a crate has to define its own type named X64V3Token and copy archmage’s hidden constant onto it. #[arcane] then trampolines into AVX2 code with no detection. What you get is undefined behavior in your own functions on CPUs without the features. Usually that is a SIGILL crash, but not always: on a CPU without LZCNT or BMI1, lzcnt and tzcnt run as older instructions and return wrong values instead of faulting. The forged type is a different type, so it unlocks only the forger’s own functions, never code that asks for archmage’s token. This compile-only check confirms the recipe works as described:

The rest

  • suppress_const_test removes the name check. Only generators that write real type paths should pass it, as magetypes’ does; the exploit suite keeps suppressed_alias to show that an aliased name compiles with it.
  • unsafe { Token::from_context() } in your code is your proof, like any other unsafe block.
  • Detection is trusted: std_detect, winarm-cpufeatures on Windows on ARM, and the Apple baseline list on macOS. A wrong answer from any of them is a wrong token.
  • The scanner is text-based (regular expressions and brace matching over comment-stripped source), not a Rust parser. Its per-file floors and its own unit tests guard against it silently seeing nothing.
  • The // SAFETY: comment in arcane.rs’s wrapper template says the token’s existence proves summon() succeeded. Tokens also come from from_context() and downcasts; the conclusion, that the features are present, still holds.

Stale statements found while writing, since fixed

  • xtask/src/soundness.rs said the generated backend impls hold “~2000 identical blocks” under a file-header contract. They held one, in sse2_baseline!; now they hold none. Fixed in 223b3a38 and 7e49ccac.
  • The tests/soundness/*.stderr files held old diagnostics that nothing compared. Removed in 76c547a3.
  • docs/SAFETY-CRITICAL.md described forge_token_dangerously() as the unchecked constructor that summon() calls; it is a deprecated alias of from_context(). Fixed in 223b3a38.
  • magetypes/src/cast.rs said width changes are not exposed on the generic types; low(), high() and split() exist. Fixed in 0088371c.
  • Moving sse2_baseline! to #[arcane] left baseline_intrinsic passing without testing the macro: its scratch crate could not resolve arcane, so the AVX call landed in a plain function and still reported E0133. The case now requires E0133 as the only error and has a compiling control. Fixed in 300e4c43.
