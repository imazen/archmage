Use native AVX-512 when a measured kernel benefits from it. Enable `avx512` on
both dependencies and forward a caller feature as shown in
[installation](@/archmage/getting-started/installation.md).

Write the tier as `v4(cfg(avx512))` or `v4x(cfg(avx512))`. `incant!` and
`#[magetypes]` then compile it only when your own crate's `avx512` feature is
on. A bare `v4` gets the same gate implicitly today; a future release removes
the implicit gate. `#[autoversion]` needs no feature: it always generates its
`v4` variant.

`w512` alone provides logical 512-bit vectors and their polyfills; it does not
enable native AVX-512. Token names remain available independently of these
Cargo choices, while use of the native backends and memory wrappers needs the
corresponding support.

The complete [linear-srgb gamma chain](@/magetypes/math/transcendentals.md)
uses [`f32x16`](https://docs.rs/magetypes/latest/magetypes/simd/generic/struct.f32x16.html) across V4, V3, NEON, WASM, and scalar. Its logical width stays
sixteen everywhere. Adding V4 to `define(f32x8)` does not turn eight lanes into
sixteen. On the V4 tokens, `f32x4` and `f32x8` lack their transcendentals,
integer conversions and raw interop. No other 128- or 256-bit type is
implemented there. A `v4` copy that uses any of those does not compile.

| Need | Choice |
|---|---|
| Portable 16-lane arithmetic | [`f32x16<Token>`](https://docs.rs/magetypes/latest/magetypes/simd/generic/struct.f32x16.html) or `define(f32x16)` |
| Existing eight-lane kernel on AVX-512 hardware | Keep the V3 variant; it remains usable |
| A different optimized V4 algorithm | Hand-written `_v4` entry alongside generated lower-tier variants |
| Mask registers or specialized instructions | Concrete `X64V4Token` / extension token plus intrinsic helpers |

Masked arithmetic is a value operation; masked memory still needs valid extent,
alignment, and active-lane semantics. Consult the
[intrinsics browser](https://imazen.github.io/archmage/intrinsics/) for supported
safe wrappers. Do not infer a checked gather/scatter API from the presence of
mask registers.

V4, V4x, and FP16 tokens prove different feature sets; the registry is authoritative.
Wider arithmetic can reduce instruction count but does not guarantee twice the
throughput. Measure memory bandwidth, reduction/shuffle work, spills, and tails
on the intended CPUs.

## What the `v4` context changes for `f32x8` code

An `f32x8` kernel compiled in the `v4` tier keeps its eight lanes. Whether the
AVX-512 features change its code depends on what the body does. From assembly
inspection with rustc 1.99.0
([results](https://github.com/imazen/archmage/blob/main/benchmarks/v4_context_asm_2026-10-06.md);
instruction selection only, no timings):

| Body | `v4` copy compared with `v3` |
|---|---|
| Multiply, FMA, rounding, reductions | The same instructions |
| Two or four `f32x8` per iteration | The same instructions; LLVM does not merge them into `zmm` |
| Compare and `blend` | The blend goes through a mask register |
| Three-input bitwise selects | One `vpternlog` |
| More than 15 vectors live in the loop | Uses `ymm16`–`ymm31` where `v3` reloads from the stack |
| A plain loop under `#[autoversion]` | `zmm` |
| The same kernel written with `f32x16` | `zmm`, twice the floats per iteration |

For 512-bit vectors, write the kernel with `f32x16`. Listing `v4` on an `f32x8`
kernel changes its code only for the rows above. Measure before keeping it: a
different instruction is not always a faster one.
